# GOOSE Network Analyzer (IEC 61850)

Высокопроизводительный анализатор локальных вычислительных сетей цифровых подстанций (ЦПС) и система мониторинга трафика **IEC 61850-8-1 (GOOSE)** в реальном времени, полностью реализованная на **Go 1.26.2**.

Проект предназначен для захвата Ethernet-кадров с GOOSE-сообщениями (`EtherType 0x88b8`), сверки сетевых потоков с эталонной конфигурацией подстанции (`.scd` / SCL) и мгновенного выявления сбоев оборудования, потерь пакетов или сетевых атак (спуфинг, инъекция пакетов, нарушение последовательности счетчиков) с гарантированной доставкой инцидентов по **TCP** и отображением в веб-интерфейсе через **WebSocket**.

---

## Технологический стек

* **Язык программирования:** Go `1.26.2`
* **Захват и фильтрация трафика:** `libpcap` + `github.com/google/gopacket/pcap` (BPF-фильтрация на уровне ядра ОС)
* **Парсинг протоколов:**
  * Нативный побайтовый разбор кадров Ethernet / IEEE 802.1Q VLAN / ASN.1 BER (GOOSE PDU) без внешних зависимостей.
  * Нативный XML-парсер конфигураций подстанции стандарта IEC 61850 (`.scd`) на базе `encoding/xml`.
* **Сетевое взаимодействие:**
  * **Анализатор $\rightarrow$ Сервер:** Выделенный постоянный **TCP-канал** с автоматическим переподключением и буферизацией (формат сообщений RFC 5424 + JSON).
  * **Сервер $\rightarrow$ Браузер:** REST API (`net/http`) + **WebSocket Hub** (`github.com/gorilla/websocket`) по паттерну Fan-Out для мгновенной доставки событий и потокового вывода консоли анализатора.
* **Хранение данных:** Потокобезопасное кольцевое хранилище в оперативной памяти (In-Memory Ring Buffer) + персистентная запись на диск в формате NDJSON (`logs/packets-YYYY-MM-DD.log`) с автоматической суточной ротацией и восстановлением состояния при перезапуске.
* **Инфраструктура:** Docker (Multi-stage build на базе `golang:1.26.2-bookworm` и `debian:bookworm-slim`), Docker Compose (`network_mode: host`, `CAP_NET_RAW`).

## Архитектура и конвейер горутин

Система разделена на два независимых бинарных файла (`analyzer` и `server`), объединенных надежным TCP-соединением:

```text
[ Сетевой интерфейс (eth0) / PCAP-дамп ]
                   │
                   ▼ (BPF: vlan and ether proto 0x88b8)
┌──────────────────────────────────────────────────────────┐
│  GOOSE Analyzer (cmd/analyzer)                           │
│                                                          │
│  1. Нативный парсер .scd ──► Сортировка эталонов (AppID) │
│  2. PREP-фаза            ──► Инициализация пула потоков  │
│  3. MAIN-конвейер горутин:                               │
│     ├─ Pcap Reader (чтение сырых кадров)                 │
│     ├─ Parser Pool (параллельная распаковка ASN.1 BER)   │
│     ├─ Sharded Workers (шардинг по AppID % NumCPU)       │
│     └─ Async TCP Client (неблокирующая отправка по TCP)  │
└──────────────────────────┬───────────────────────────────┘
                           │ TCP (:5514, RFC 5424 + JSON)
                           ▼
┌──────────────────────────────────────────────────────────┐
│  Controller & Collector Server (cmd/server)              │
│                                                          │
│  ├─ TCP Receiver (:5514) ──► Прием телеметрии и ошибок   │
│  ├─ EventStore           ──► RAM + Диск (packets-*.log)  │
│  ├─ Process Manager      ──► Управление процессом захвата│
│  └─ HTTP API & WS Hub (:5000) ──► Real-time дашборд      │
└──────────────────────────────────────────────────────────┘
```

### Ключевая оптимизация: Sharded Worker Pool
При проверке GOOSE-сообщений критически важен строгий порядок пакетов внутри каждого потока (`AppID`), так как валидатор проверяет инкремент счетчиков `sqNum == prev.sqNum + 1` и переходы состояний `stNum`.
Чтобы задействовать все ядра процессора и избежать гонок данных (Race Conditions) без блокировок `sync.Mutex` на каждый пакет, применено **шардирование каналов по ключу `AppID % numWorkers`**:
* Разные GOOSE-потоки обрабатываются параллельно на разных ядрах CPU.
* Пакеты одного и того же `AppID` всегда попадают в один и тот же воркер строго в порядке их прихода из сети.

## Отслеживаемые ошибки и аномалии GOOSE

Анализатор сопоставляет каждый перехваченный пакет с эталонной конфигурацией `.scd` (используя бинарный поиск по `AppID` за $O(\log N)$) и предыдущим пакетом потока в пуле:

| Категория | Проверка / Флаг | Уровень (Severity) | Описание |
| :--- | :--- | :--- | :--- |
| **Неизвестный трафик** | `GhostGoose` | `warning` | Обнаружен GOOSE-пакет, отсутствующий в `.scd` конфигурации подстанции (`AppID`, `DstMAC` или `GoID`). |
| **Целостность потока** | `SqNumErr` | `error` | Нарушение последовательности `sqNum` (потеря пакета, скачок счетчика или некорректный сброс). |
| **Целостность событий** | `StNumErr` | `error` | Изменение номера события `stNum` без сброса `sqNum` в `0` или скачок `stNum` больше чем на `1`. |
| **Дублирование** | `DuplicateGoose` | `error` | Повторное получение пакета с идентичными `AppID`, `stNum` и `sqNum`. |
| **Конфигурация** | `ConfRevErr` / `ConfRevChng` | `error` | Несовпадение ревизии конфигурации `confRev` с `.scd` файлом или её изменение на лету. |
| **Безопасность L2** | `SrcMacErr` | `error` | Изменение MAC-адреса источника (`src_mac`) в рамках установленного GOOSE-потока (признак ARP/MAC-спуфинга). |
| **Тегирование 802.1Q** | `VlanAdded` / `VlanRemoved` / `VidChng` / `VprChng` | `warning` / `error` | Появление/снятие метки VLAN или изменение `VLAN ID` / `VLAN Priority` относительно предыдущего пакета. |
| **Синхронизация времени** | `ClockFailure` / `ClockInvalidAccuracy` | `critical` / `warning` | Флаг сбоя часов источника (`0x40` в поле `t`) или недопустимый класс точности времени (`> 24`). |
| **Состояние IED** | `DatasetEmp` / `NdsComm` | `warning` | Пустой набор данных (`numDatSetEntries == 0`) или установленный флаг необходимости наладки (`ndsCom`). |

## Быстрый старт

### Вариант 1: Запуск через Docker Compose (Рекомендуется)

```bash
# Сборка образов (включает автоматический прогон всех тестов) и запуск в фоне
docker compose up --build -d

# Просмотр логов сервера
docker compose logs -f
```
После запуска веб-интерфейс будет доступен по адресу: **`http://localhost:5000`**.

---

### Вариант 2: Локальная сборка и запуск (Linux)

1. **Установите системные заголовки `libpcap`:**
   ```bash
   sudo apt-get update && sudo apt-get install -y libpcap-dev
   ```

2. **Прогоните тесты (с детектором гонок данных):**
   ```bash
   go test -race -v ./...
   ```

3. **Соберите бинарные файлы:**
   ```bash
   mkdir -p bin
   go build -o bin/analyzer ./cmd/analyzer
   go build -o bin/server ./cmd/server
   ```

4. **Запустите сервер управления:**
   ```bash
   ./bin/server
   ```

5. **Автономный запуск анализатора из CLI (опционально):**
   ```bash
   # Оффлайн-режим (чтение из .pcapng дампа):
   ./bin/analyzer path/to/config.scd /path/to/dump.pcapng

   # Онлайн-режим (захват с интерфейса eth0, требуются права root или CAP_NET_RAW):
   sudo ANALYZER_IFACE=eth0 ANALYZER_TCP_SERVER=127.0.0.1:5514 ./bin/analyzer path/to/config.scd
   ```

## Справочник API и переменных окружения

### Переменные окружения

| Переменная | По умолчанию | Описание |
| :--- | :--- | :--- |
| `TCP_ADDR` | `0.0.0.0:5514` | Адрес и порт TCP-сервера для приема событий от анализатора. |
| `HTTP_ADDR` | `0.0.0.0:5000` | Адрес и порт веб-интерфейса и REST/WS API. |
| `ANALYZER_BIN` | `./bin/analyzer` | Путь к скомпилированному бинарному файлу анализатора. |
| `ANALYZER_IFACE` | `eth0` | Сетевой интерфейс для перехвата пакетов в `online`-режиме. |
| `DEFAULT_DUMP` | `/root/dumps/nergenA1_A2dump_nodup.pcapng` | Путь к файлу дампа по умолчанию для `offline`-режима. |
| `UPLOAD_DIR` | `uploads` | Директория для загруженных через интерфейс `.scd` файлов. |
| `CONFIG_DIR` | `configs` | Директория для хранения `history.json`. |
| `LOG_DIR` | `logs` | Директория для сохранения суточных логов `packets-YYYY-MM-DD.log`. |

### Основные эндпоинты

* `GET /` — Веб-панель управления анализатором.
* `GET /ws` — WebSocket-соединение (события `new_event`, `output`, `subscribed`).
* `GET /api/events?limit=100&severity=error` — Получение списка зафиксированных ошибок с фильтрацией по уровню важности.
* `GET /api/stats` — Агрегированная статистика по общему числу ошибок и уровням `severity`.
* `GET /api/logs/download?date=YYYY-MM-DD` — Скачивание суточного файла логов в формате NDJSON.
* `POST /upload` — Загрузка новой `.scd` конфигурации (`multipart/form-data`).
* `GET /history` и `POST /delete_config` — Управление историей конфигураций.
* `POST /start` и `POST /stop` — Запуск и корректная остановка (`SIGTERM`) процесса анализатора.
